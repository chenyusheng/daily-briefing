1 HTML/CSS/JS 基础 + ES6 ▼
高频必问 ES6 CSS

Q: ES6 常用特性及与 ES5 关键区别？

① 箭头函数 — this 绑定在定义时，非调用时。() => {} 让 React 组件方法不再需要 .bind(this)。 ② Promise + async/await — 解决回调地狱。串行用 await，并行用 Promise.all。 ③ 解构 + 展开运算符 — const { name } = props，[...arr1, ...arr2] 补充：ES6 模块化 import/export 让前端工程化成为可能；let/const 块级作用域解决 var 变量提升隐患。

Q: CSS 水平垂直居中，三种方法？

① Flexbox（最常用） display:flex; justify-content:center; align-items:center ② Grid（更简洁） display:grid; place-items:center ③ 绝对定位+transform position:absolute; top:50%; left:50%; transform:translate(-50%,-50%) 适用场景：Flex 一维布局、Grid 二维布局、绝对定位弹窗/toast。

2 HTTP 协议 + 缓存 + 跨域 ▼
必考 状态码 跨域

Q: 强缓存 vs 协商缓存？

强缓存（不发请求） Cache-Control: max-age=31536000 → 返回 200 (disk cache) 协商缓存（发请求验证） ETag / If-None-Match → 内容哈希比对 Last-Modified / If-Modified-Since → 时间比对 返回 304 Not Modified 项目实战： · HTML → 协商缓存或不缓存（保证即时更新） · CSS/JS → 强缓存 + contenthash 文件名（改了就换名） · 图片/字体 → 强缓存一年

Q: 跨域怎么解决？

同源 = 协议 + 域名 + 端口，任意不同则跨域。 解决方案（按优先级）： ① CORS：后端设置 Access-Control-Allow-Origin ② 开发环境 proxy：Vite/Webpack devServer.proxy ③ Nginx 反向代理：生产环境同域转发 ④ JSONP：仅 GET，基本淘汰 为什么有同源策略？ 防止 CSRF — A 站脚本不能读 B 站的 Cookie。安全是浏览器替用户做的约束。

3 UI 一致性 · 用户体验 · 响应式设计 ▼
响应式 移动端 组件库

Q: 怎么做响应式适配？踩过什么坑？

方案演进： 早期：@media (max-width: 768px) 固定断点 现在：Rem + 动态基准值 + Flex/Grid 弹性布局 踩过的坑： ① Retina 屏 1px 边框变 2px → transform: scaleY(0.5) + 伪元素 ② iOS 橡皮筋回弹 → body { overscroll-behavior: none } ③ 300ms 点击延迟 → meta viewport 加 user-scalable=no 组件库：Ant Design 自带响应式，二次封装时用 CSS Variables 管理主题变量，而非硬编码颜色。

4 React.js 深入 · Fiber · Hooks ▼
核心难点 Fiber Hooks

Q: Fiber 架构解决了什么？

React 15 问题：递归渲染不可中断，组件树大会卡顿。 Fiber 三大改进（React 16+）： ① 可中断的异步渲染 — 大任务拆成小碎片 ② 优先级调度 — 用户输入 > 动画 > 数据更新 ③ 双缓冲 — current + workInProgress 两棵树交替，渲染完一次性提交 一句话：把"同步一口气渲染"变成"可暂停、可恢复、可插队的增量渲染"。

Q: Hooks 使用规则和常见陷阱？

两个铁律： ① 只在最顶层调用，不在条件/循环里（React 靠调用顺序匹配状态） ② 只在函数组件或自定义 Hook 里调用 四大陷阱： ① 闭包陷阱 — useEffect 依赖漏了变量，读到旧值 解法：加依赖，或用 useRef ② useState 异步更新 — 连续 setCount(count+1) 只加 1 解法：setCount(prev => prev+1) ③ useMemo/useCallback 滥用 — 不是所有函数都要包 仅当：传给 memo 子组件 / 作为其他 Hook 依赖时 ④ 自定义 Hook — 抽通用状态逻辑 如：useDebounce、useFetch、useLocalStorage

5 项目架构 · 模块化 · Webpack/Vite ▼
构建工具 架构 高频

Q: Webpack 和 Vite 的区别？怎么选？

核心差异： Webpack — 打包成 bundle → 启动 Dev Server（慢） Vite — 启动 Server → 浏览器按需 import → 按需编译（秒开） Vite 开发时基于浏览器原生 ESM，生产用 Rollup 打包。 选型：新项目无脑 Vite。老项目重度依赖 webpack loader 时需评估迁移成本。

Q: 大型项目代码怎么组织？

src/
├── pages/       页面组件，路由对应
├── components/  通用组件，跨页面复用
├── hooks/       自定义 Hook
├── utils/       纯函数工具
├── services/    API 请求层
├── store/       状态管理
├── styles/      全局样式 + 主题变量
└── types/       TS 类型定义
分层原则： ① 页面不直接调 axios → 通过 services 层 ② 通用组件不放业务逻辑 → props 传入 ③ 跨页面状态用 Context/Zustand，组件内用 useState ④ 常量集中管理，不散落魔法字符串

Q: 页面加载慢，怎么排查和优化？

排查三步走： ① 看大指标：Lighthouse / Performance 面板 LCP > 2.5s 加载慢 | FID > 100ms 交互慢 | CLS > 0.1 布局偏移 ② 看网络：Network 瀑布图 哪个资源最大？哪些阻塞渲染？接口是否太慢？ ③ 对症下药： 首屏慢 → 路由懒加载 + 组件按需加载 包太大 → Code Splitting + Tree Shaking 图片大 → WebP + 懒加载 + 响应式 srcset 重复渲染 → React DevTools Profiler + memo 接口慢 → 缓存/防抖节流/骨架屏优化感知 关键：优化前先测量，优化后用数据对比。

Q: Node.js 在项目中的实际应用？

三大实际场景： ① BFF 层 — 前端定制的中间层，聚合多后端接口，减少请求数 ② SSR — Next.js 服务端渲染，首屏快 + SEO 友好 ③ 代理服务 — 开发环境 proxy 解决跨域 核心理解： · 单线程事件循环 → 适合 I/O 密集（读文件/查数据库） · CPU 密集任务（图片处理）→ 用 worker_threads · 中间件洋葱模型（Express/Koa）是精髓 · npm 生态让 Webpack/Vite/ESLint 天然运行在 Node 上

Q: 讲一下你对接大模型 API 的经历？常见的报错怎么排查？

真实场景：我做过 AI skill 评测引擎，对接多家大模型 API（OpenAI 兼容格式为主）。

① 401 / 认证失败
· 检查 key 是否过期/额度用尽（DeepSeek 等国内平台余额不足会报 401 而非 402）
· 确认 base_url 是否正确（国内版 / 国际版端点不同）

② 429 / 限流
· 并发过高触发 → 加指数退避重试（retry-after 头）
· 分批请求 + 控制并发数（信号量）

③ 超时 / 断流（流式最常见）
· 设置 AbortController 超时中断
· 流式响应中断 → 断点续传思路：记录已渲染内容，重连后增量补齐

④ 参数不兼容
· 各家模型参数名不同（max_tokens vs max_completion_tokens）→ 抽象一层统一适配层，这是做聚合平台的必修课

Q: SSE 流式对话是怎么实现的？EventSource 和 fetch 流式有什么区别？

SSE 全链路：
① 前端发请求 → 后端以 text/event-stream 返回
② 每块数据 data: {json}\n\n 格式
③ 前端用 fetch + ReadableStream 逐块读取渲染（打字机效果）

EventSource vs fetch 流式：
· EventSource：自动重连、只支持 GET、不能自定义 headers（无法带 Authorization）→ 多数场景不适用
· fetch + ReadableStream：支持 POST + 自定义 headers，手动解析，可控性强 → 生产首选

核心代码： 

const res = await fetch(url, { method: 'POST', headers, body, signal });
const reader = res.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value);
  // 按 SSE 协议解析 data: 行，增量 setState
  appendToStream(parseSSE(chunk));
}

踩坑：流式输出必须防抖批量渲染（每块都 setState 会卡 UI），用 requestAnimationFrame 或批次合并；中断后要处理未闭合的 JSON（半行数据）。

Q: 你了解 RAG 吗？线上有哪些难题？

RAG 流程：文档 → 切分 chunk → embedding 向量化 → 存入向量库 → 检索 TopK → 拼进 prompt → LLM 生成

三大优化手段：
① Chunk 切分优化 — 固定长度切分会割裂语义；按段落/标题切分 + 重叠窗口（overlap）保上下文连续
② Embedding 选型 — 中文场景用中文向量模型（如 bge-m3），通用模型中文效果差
③ 检索质量 — TopK 调参 + 重排（rerank）模型，先粗筛再精排

线上难题：
· 幻觉 — 检索不到相关知识时模型编造 → 兜底策略：检不到就明说"资料库没有"，不要硬答
· 召回率低 — 用户问法和文档措辞不同 → 查询改写（query rewrite）+ 混合检索（关键词+向量）
· 延迟 — 向量检索慢 → 索引优化 + 缓存高频问题
· 知识更新 — 向量库重算成本高 → 增量更新 + 版本管理

Q: 两套主流 AI 前端架构，你怎么设计？（文档问答 + 网页助手）

架构一：企业私有文档问答平台
前端：文档上传页 + 对话页 + 引用来源展示
链路：上传 → 解析 → 切分 → 向量化入库 → 提问 → 检索 → 生成 → 回答带引用
前端关注点：大文件上传（分片/断点续传）、进度条、引用来源可点击跳原文

架构二：网页端 AI 智能助手（类似 Copilot）
前端：悬浮球 → 对话面板 → 支持选择上下文（当前页面/选中文本）
链路：用户选中内容 → 连同问题发给后端 → 流式返回
前端关注点：选择器与页面 DOM 交互、上下文注入、流式渲染、多会话管理
